# Interface Contracts — v1 (LOCKED)

These are the agreed shapes where Person A's ingestion lane hands off to Person B's
analysis lane. Changing anything in this file requires a PR approved by BOTH people.

Adopted: 13 July 2026 (Step 7). Decisions and rationale recorded inline.

## 1. analysis_jobs table

| Column | Type | Notes |
|---|---|---|
| id | uuid PK | generated by API |
| user_id | uuid FK | owner; every query filters on this (constitution rule 1) |
| doc_id | uuid FK | the document under analysis |
| doc_version_hash | text | SHA-256 of the exact version analyzed (immutability rule) |
| state | text | see state machine below |
| retry_count | int | default 0 |
| error_reason | text NULL | machine-readable category + short message; NEVER document content |
| created_at | timestamptz | set by API on insert |
| started_at | timestamptz NULL | set by worker on first pickup |
| finished_at | timestamptz NULL | set by worker on terminal state |

### State machine

```
queued -> running -> succeeded
queued -> running -> failed          (after retries exhausted)
running -> queued                     (transient failure, retry_count += 1)
```

DECIDED — retry semantics: transient failures (timeouts, connection errors) send the
job BACK TO queued with retry_count incremented; max 3 retries with exponential
backoff, then state=failed and the job lands in the dead-letter queue. Rationale:
"a queued job is a queued job" — the worker pickup logic stays identical for first
attempts and retries, which is simpler than a special resuming-failed path.

DECIDED — writer rules: the API writes ONLY the initial row (state=queued). The
worker owns every transition after pickup. Nobody else writes this table.
Terminal states (succeeded/failed) are never overwritten.

## 2. Findings JSON (one finding object)

```json
{
  "category": "inconsistency",
  "severity": "high",
  "block_ids": ["BLOCK_4", "BLOCK_19"],
  "evidence_quote": "the monthly rent shall be Rs. 50,000 [...] a monthly rent of Rs. 60,000",
  "explanation": "Clause 3 (BLOCK_4) states monthly rent of Rs. 50,000, but clause 14 (BLOCK_19) states Rs. 60,000. These amounts conflict and one must be corrected before signing.",
  "verification": "verified",
  "confidence": "standard"
}
```

### Field contract

- `category`: one of the 12 generic clause categories (termination, liability,
  indemnity, payment, confidentiality, auto_renewal, governing_law, penalties,
  intellectual_property, arbitration, non_compete, force_majeure) OR
  `"inconsistency"` OR `"missing_clause"`. Lowercase snake_case, exactly these values.
- `severity`: `"high"` | `"medium"` | `"low"` | `"info"`.
- `block_ids`: array of anchor ids. EXACTLY 2 for category=inconsistency; exactly 1
  otherwise; EMPTY for category=missing_clause (there is nothing to point at —
  the finding is about absence).
- `evidence_quote`: verbatim text from the document. For inconsistencies, the two
  conflicting spans joined with `" [...] "`. For missing_clause: empty string.
- `explanation`: why this matters, in plain language. No legal advice phrasing.
- `verification`: `"verified"` (quote matched to source by the deterministic verifier)
  | `"unverified"` (match failed — SHOWN but flagged, never silently dropped,
  constitution rule 6). missing_clause findings are always `"verified"` because the
  playbook/category check is deterministic.
- `confidence`: `"standard"` | `"needs_review"` (set to needs_review when the entailment
  pass score is below threshold, or verification is "unverified").

### Storage

DECIDED: `analysis_results` table — one row per finding. Columns: id uuid PK,
job_id FK, user_id FK (denormalized for RLS), doc_id FK, doc_version_hash,
category, severity, verification, confidence (extracted for filtering/indexing),
payload JSONB (the full finding object), created_at. Findings are immutable once
written; reviewer decisions (accept/edit/dismiss) go in a separate table later —
they never mutate the AI's original output (audit-trail principle).

## 3. Boundary behaviors

DECIDED — (a) polling shape: `GET /jobs/{id}` returns
`{"job_id", "state", "retry_count", "created_at", "started_at", "finished_at",
"error": {"category", "message"} | null}`. While state is queued/running the client
polls every 3 s. When succeeded, `GET /jobs/{id}/findings` returns the ordered array
of finding objects (verified first, then unverified, each group sorted by severity).
No document text ever appears in the jobs endpoint — only in the findings payloads.

DECIDED — (b) unverified findings: stored like any finding (verification=
"unverified", confidence="needs_review"), returned by the findings endpoint, and
the UI must render them in a visually distinct "Unverified — quote could not be
matched to the document" section. They count in the findings total. They are never
exported as verified.
